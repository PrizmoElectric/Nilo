[x] `Formation.RAIN` added to ArrowManifestManager.java — behaves unlike
    the other three (no floating pre-stage, no auto-conjure, no per-tick
    positioning): `/arrow-shoot` while in this formation calls castRain()
    instead of releasing floating arrows. castRain() resolves a target
    center (self position, or eye+look flat projection for "aim" mode —
    deliberately not a real block raycast, arrows just fall with real
    gravity from a fixed height and land wherever terrain actually is),
    charges a hunger cost scaling with count (ceil(count/20)), and arms a
    staggered spawn queue (one arrow every 2 ticks) drained from tick() —
    reads as "raining" over a few seconds instead of dumping the whole
    count at once. 10s cooldown, ticks down regardless of current
    formation. New PlayerState fields: rainCount (1-500, default 100),
    rainTargetSelf, rainLifeDrainEnabled, rainCooldownTicks,
    rainSpawnRemaining/Cooldown, rainCenter.

[x] Real physics, not the floating-noClip trick every other arrow group in
    this class uses — Rain arrows have gravity ON and noClip OFF from the
    moment they spawn, so they actually fall and can be dodged (explicit
    user requirement: "the enemy is allowed to try and dodge the arrows").
    Short-lived: force-discarded RAIN_ARROW_LIFETIME_TICKS (60 = 3s) after
    spawning regardless of whether they landed or hit anything — simpler
    and more robust than detecting "on ground," and keeps concurrent
    entity count bounded even at rainCount=500 (worst case ≈ spawn-rate ×
    lifetime, never the full cast count alive at once — this is what
    protects the FPS/entity-count risk flagged when this was still just a
    wishlist item).

[x] Resource cost: hunger first (down to 0, using the same foodLevel>0
    gating the earlier hunger-refund bugfix established), then — only if
    the player has opted in via RED TERMINAL's life-drain toggle — health,
    but NEVER past 50% of max health (RAIN_LIFE_HEALTH_FLOOR). Any cost
    still unpaid after both is simply forgiven; Rain always fires once
    cast, matching this class's existing "never block the action" cost
    philosophy (see conjureOne()'s NO_ARROW_HUNGER_CHANCE design).

[x] NEW — RainArrowOwnerImmunityMixin.java (com.zote.contextmod.mixin).
    Verified via javap against the actual mapped 1.20.1 (Yarn build.10)
    ProjectileEntity class (not assumed) that vanilla's owner-exclusion is
    TEMPORARY, not permanent — a leftOwner flag flips true once a
    projectile is judged to have travelled far enough from its owner's
    hitbox, after which canHit(Entity) allows the owner again (the
    well-known "shoot an arrow straight up, it falls back and hits you"
    vanilla behavior — same mechanism). Rain arrows spawn 15 blocks above
    the caster, so leftOwner flips almost immediately, meaning a falling
    Rain arrow absolutely could hit the summoner on the way down under
    plain vanilla rules — especially in self-target mode, which aims
    arrows at the caster's own position on purpose. This is the same class
    of bug already found and fixed once this session for Barrage (a
    different mechanism — noClip toggling — but the same lesson: verify,
    don't assume, arrows can't hit their owner). Injects into
    ProjectileEntity.canHit(Entity) (HEAD, cancellable), forcing false when
    the checked entity is the arrow's own owner AND the arrow carries the
    new RAIN_ARROW_TAG — scoped so it never touches any other projectile
    in the game, including this project's own other arrow groups (which
    never target their owner's position anyway). require=0 in
    solsai.mixins.json, matching EnchantmentHelperMixin's own documented
    reasoning in that same file: an unresolved mixin target fails the
    WHOLE mod's load under this project's defaultRequire=1, too large a
    blast radius for one safety mixin on a live server. **If this doesn't
    resolve, the log will show a conflict/0-targets warning for
    RainArrowOwnerImmunityMixin specifically after a restart — check for
    that BEFORE trusting self-target mode is actually safe.**

[x] BUG FIX — conjureOne()'s 5%-chance hunger charge called
    `hunger.setFoodLevel(Math.max(0, foodLevel - 1))` and set
    `chargedHunger = true` UNCONDITIONALLY. At foodLevel == 0 that call is a
    clamped no-op — nothing is actually paid — but the arrow still got
    tracked as hunger-funded. Dismissing it later still refunded a genuine
    +1 (no clamp stops an increase from 0), handing back a real food point
    for a cost that was never actually charged. Gets worse the longer a
    summon/dismiss test session runs, since repeated cycling naturally
    drives hunger down toward 0 first — exactly where the bug kicks in —
    matching the user's exact report. Confirmed shields are NOT affected by
    this class of bug: their refund only ever touches `exhaustion` (never
    `setFoodLevel` directly), and exhaustion has no mechanism to grant food
    when reduced — at worst it under-refunds, never over-refunds.
    Fix: gate the charge on `foodLevel > 0` BEFORE clamping, so
    `chargedHunger` only ever becomes true when a real point was paid —
    "funded" now means what it says.

[x] BUG FIX — dismiss didn't actually stop Barrage/Circles auto-spawn.
    Root cause, traced (not guessed): dismiss() cleared the current arrows
    but never touched PlayerState.formation, so autoConjure() — driven
    purely by "formation != MAGE_CIRCLE" — refilled the group again on the
    very next timer tick, same as if dismiss never ran. User's repro
    matched exactly ("most of the time it fails to stop it" — because
    within ~4 ticks the arrows were visibly back). Fixed: new
    PlayerState.autoSpawnPaused, set true by dismiss(), checked by
    autoConjure(), cleared by any explicit "give me more" action
    (manifest/manifestBurst/setFormation/setFireMode).

[x] BUG FIX — Barrage arrows killed the player on release. Confirmed live,
    at the moment of firing (not while floating). Root cause: Barrage
    arrows sit BEHIND the player; releaseArrow() re-enables collision
    (setNoClip(false)) and gives forward velocity in the same instant, so
    the arrow's flight path necessarily passed back through the player's
    own hitbox — Mage Circle/Circles arrows never had this because they're
    always positioned in FRONT. Fixed: releaseArrow() now snaps every
    arrow to a safe muzzle point (eye + look*0.5) before re-enabling
    collision, applied unconditionally (harmless one-frame jump for
    formations already in front, closes the same risk for any future one).

[x] Fast-fire "spin-up" visual glitch (Machine Gun + Barrage/Circles) —
    diagnosis: not formation-math lag (positions are recomputed fresh every
    tick, no server-side catch-up), but standard Minecraft client entity
    interpolation — arrows used to always spawn at eye and only reach their
    real slot on the NEXT tick, so a near-instant Machine Gun release could
    fire before the client's smoothing finished. Fixed: conjureOne() now
    computes the real intended position (Barrage's random offset / Circles'
    slot center) and spawns there directly for those two formations. Mage
    Circle untouched (manual conjure only, never flagged as having this).

[x] Circle formation positioning reworked. Was: fixed 4-slot list

    pitch. One accepted minor artifact: a brief visual snap exactly at the
